# vep-cache-converter

`vep-cache-converter` is a command-line binary, shipped in every release beside `vep` and `vep-cache-builder`, that prepares data files for the annotator. Without a subcommand it copies a flat JSON (JavaScript Object Notation) transcript cache into the per-chromosome layout `vep-cli` loads, validating each region file; `convert-plugin-data` converts a tabix-indexed plugin data file into the binary annotation store (`.vpd` data plus `.vpdi` index) that the `vep-builtins` plugins memory-map at runtime. No crate depends on it; it depends on `vep-builtins` for its record and store types and on `vep-cli` for the regulatory shard parser.

## How it works

`convert-plugin-data` follows one data line from the input file to a verified store. An `--output` that is the input table or a path the table's index is read from (`<table>.tbi`, `<table>.csi` and the same two names on the table's stem; `kept_paths`), or whose `.vpdi` path is, as the path is given or as a symbolic link there names it, is refused before anything is read or written, since the store's files replace whatever lies at the paths they are published at (`is_same_file`). A column index the store's index cannot record is refused at the same point, as are `--chr-col` and `--start-col` naming other columns than the table's tabix index was built on, and any `--end-col` given without `--ref-col`, or `--zero-based` but one given with `--end-col` and `--ref-col` under an index of zero-based starts, unless the flags name the end column and the starts the index declares or single one-based positions (`indexed_layout`; an index of tabix's `vcf` or `sam` preset declares one-based starts and no end column), the refusal naming the flags that match the index; flags that name single one-based positions where the index declares an end column or zero-based starts draw one warning line, which names the flags that match the index, and convert (`check_indexed_columns`). `stream_table` reads the input once through a BGZF (blocked gzip) reader over a `HashingReader`, so the SHA256 and length it returns are of the bytes the conversion read, keeps the last `#` line before the first row as the column names, or, under no `#` line, the first row itself when its start cell leads with no integer, the bare header the plugins' tabix reader takes (`parse_header`; a `#` line after the first row is a comment), and reads each data line into a row: the chromosome from `--chr-col`, the start from `--start-col` read to its leading integer as tabix reads it (plus one when `--zero-based` is set), the end by the tabix reader's span rule (`TabixConfig::record_end`: with `--ref-col`, the `--end-col` column's `END` key at or past the start, else the allele's span; without `--ref-col`, the `--end-col` cell's leading integer; the start alone without `--end-col`), and the line's cells, borrowed from the line and never copied. A line with fewer columns than `--chr-col` or `--start-col` needs is skipped; a start that no integer leads is an error. A line is split with its line end alone removed, as the plugins read it through tabix, so a last cell keeps its trailing whitespace and an empty last cell stays a cell ([Tabix indexes and `.vpd` stores](../../docs/plugins/data-files.md#tabix-indexes-and-vpd-stores)). Each row goes to the store as it is read: `BinaryStoreWriter::stream` from `vep-builtins` begins the store at the first row placed, and `BinaryStoreStream::push_row` encodes the row and appends it to a scratch file of its chromosome, so no row outlives its line and the conversion holds, of each chromosome, its name and a few counts. When the table ends, `BinaryStoreStream::finish` writes the column table and the records to the `--output` path, the chromosomes in string order (`1`, `10`, `11`, `2`) and a chromosome's rows by start alone, the rows at one start in the file's order, the order `tabix` prints them in; a chromosome whose rows arrive out of start order, which no table `tabix` indexed holds, is put in that order by a stable sort of its rows' starts and offsets, 16 bytes a row of that chromosome. It writes, to the same path with the extension `.vpdi`, the layout flags the records were read by, the SHA256 and length of the input and of the data file, and the chromosome and position index; the index ends with the SHA256 of its own bytes; each file is written whole under a scratch name beside its own (the file's name, the process id, `data` or `index`, and `.partial`) and renamed into place, the data first and the index last, a path that is a symbolic link at the file its chain of links names, so a `vep` run that starts during a conversion finds no part-written store and one that holds the previous store open keeps it; a chromosome's rows and its position entries wait in numbered scratch files beside the data file (the data file's name, the process id, `rows` or `starts`, the chromosome's number, and `.partial`), a rows file removed once the data file holds its rows, so a conversion needs room beside the output for the store and one chromosome's rows more; the data and index scratch files lie under the writer's exclusive lock while they are written, a numbered scratch file is held by the conversion that holds its data scratch file locked, and the scratch files of the same output that no conversion holds, which a killed conversion left, are removed before any is created; a cell, column name or chromosome name over 65,535 bytes, or a header or row of more than 65,535 cells, is refused naming the row and the length, since the store's length fields are 16 bits wide, a position of more than 4,294,967,295 rows is refused naming the position, since an index entry counts rows in 32 bits, the previous store's index is removed once both scratch files are written whole, before the data is renamed, so a conversion refused or failed before that removal, while it reads its table included, leaves a previous store whole and no scratch file behind, and one that fails after it, at a rename, leaves neither file; a plugin whose table reads by other columns refuses the store, naming the flags that rebuild it, and reads the table through tabix, as does a plugin whose table, or whose store's data file, differs in length or SHA256 from what the index records, naming which, or whose store's index differs from the SHA256 it ends with. Unless `--no-verify` is set, `open_table` opens the input through `TabixAnnotator`, the reader the plugins use without a store, before anything is read or written, so an input without its index fails with no store left behind, and `stream_table` records each row's start and end as it reads it, 16 bytes a row in a scratch file of the row's chromosome (`Spans`, under the stream's scratch names in the role `spans`), so the verification probes what the table holds, whatever the store was given. `probe_positions` reads those spans twice before the store is published, once to count the distinct record starts and once to take the probes: every start when the file holds at most 1,000 of them or `--verify-all` is set, otherwise every n-th start from the first, n the smallest stride that keeps the sample at 1,000 starts or fewer, so a conversion checks the same starts on every run, and for each checked start, the start and each of its records' end, midpoint, the position past its end and the one before its start; the position past an end is left out where it lies past the last position the table's index holds (2^29 for a `.tbi`), where the tabix reader returns no row whatever the file holds. After the write, `verify_concordance` reopens the store through `BinaryAnnotator`, the reader the plugins use at runtime; `verify_probes` queries each position through both readers and compares their records in the order each returns them, span and every cell (`record_line`), then asks the store for the position again through its batch query, alone and then with the positions beside it in batches of 64, in order and reversed, against the same answer of the table; the first ten mismatches are printed, the store's two files are removed where the writer published them, a symbolic link at an output path staying (`remove_store`), and the exit is non-zero; a verification that does not run to its end (a query the table's index cannot answer) removes them the same way.

The cache mode follows one region file. `convert_cache` creates the output directory, writes `CHECKSUMS.sha256` there as the one line that lists no file (`CacheManifest::mark_unfinished`) and, after the transcript and variation files, `read_info_json` reads `info.json`, parses it, checks what the runtime's cache resolution reads (an object with a non-empty `species` and `assembly`, a `contig_order`, `variation_cols` or `cell_types` that is a list of strings when present, a `regulatory_schema` that is a whole number when present, and a `bam`, the alignment file the cache's transcript models were edited against, or a `source_type`, the transcript set the cache holds, that is a string when present) and logs its `species` and `assembly`; after the regulatory files, `copy_info_json` writes it with the `regulatory` marker set when `copy_regulatory_files` wrote a shard, `cell_types` and `regulatory_schema` passing through, all three removed otherwise, and copies `chr_synonyms.txt` beside it when the source has one; a missing, unparseable or unusable `info.json` is an error. `convert_data_files` runs over `transcripts/`: it lists the directory in file-name order, takes each `.json` file, and `parse_region_filename` splits the stem at its last underscore into chromosome and range, so `LRG_485_1-1000000` yields the LRG (Locus Reference Genomic) sequence name `LRG_485` as its chromosome; a stem that does not fit is skipped with a warning. The content must parse as JSON (a parse failure is an error) and be an array (anything else is skipped with a warning); its length is counted and the text is written unchanged to `<output>/transcripts/<chr>/<start>-<end>.json`, the shard layout `vep-cli` enumerates. `copy_variation_files` runs over `variations/`, which holds the files the Ensembl VEP dumper writes: `all_vars.gz` with its `.csi` or `.tbi` index, or `{start}-{end}_var.gz` region files, under `variations/<chr>/`, or carrying a `{chr}_` prefix directly under `variations/`. `split_flat_variation_name` finds the chromosome in a flat name by trying each underscore until what follows is a variation file name, and each file is copied byte for byte to `<output>/variations/<chr>/`; any other name, flat or under `<chr>/`, is skipped with a warning. An `all_vars.gz` without its index is an error, as is a `.json` file under `variations/`: the annotator reads the dumper's files only. A missing `variations/` directory is a warning, not an error. `copy_regulatory_files` runs over `regulatory/`: it refuses a tree whose metadata lacks the `regulatory_schema` this build reads, loads and copies the binding matrices table `regulatory/binding_matrices.json`, then copies each `regulatory/<chr>/<start>-<end>.json` or `.json.gz` shard byte for byte once it parses as the annotator parses a shard (`vep_cli::regulatory::count_shard_features`, against the metadata's `cell_types` list and the table); a shard that does not is an error, any other entry is skipped with a warning, and a missing `regulatory/` directory writes no marker. `CacheManifest::write` then lists every file of the output directory, the manifest itself excepted, in `CHECKSUMS.sha256`, the file `vep-cli` checks each cache file it reads against. A conversion that fails or is killed before that last write leaves the first line, and `vep` refuses the directory by name; converting into it again completes the cache.

## Modules

| Module    | Role                                                                                 |
| --------- | ------------------------------------------------------------------------------------ |
| `main.rs` | The whole crate: the clap definitions, both conversion paths and the unit tests. |

The functions of `main.rs`:

| Function                | Role                                                                                                        |
| ----------------------- | ----------------------------------------------------------------------------------------------------------- |
| `main`                  | Switches on dropping a write standard error refuses, runs `run` and, when it fails, prints the one line `ERROR: [cache-converter] <message>` on stderr and exits 1. |
| `run`                   | Installs the `tracing` subscriber on stderr at INFO level, parses the command line and dispatches.          |
| `resolve_json_dir`      | Requires `--json-dir` and checks that the path exists.                                                      |
| `log_lines_carry_colour` | Whether the log lines carry colour codes: only where standard error is a terminal and `NO_COLOR` is unset or empty. |
| `counted`, `counted_as` | A count beside its noun as a log line or an error words them: `1 region`, and `0 regions` or `2 regions` for every other count; `counted_as` takes a noun whose plural is not the singular with an `s` (`1 entry`, `2 entries`). |
| `convert_plugin_data`   | Drives read, write and verification for one plugin data file; logs record counts, sizes and timings.        |
| `is_same_file`          | Whether two paths name one file, for the refusal of an `--output` that is the input table or an index path of it. |
| `kept_paths`            | The paths a store's files may not be written at: the input table and the four paths its index is read from. |
| `layout_flags`          | The `convert-plugin-data` flags of a layout, as a refusal or a warning names them. |
| `IndexedLayout`, `indexed_layout` | What a table's tabix index declares: its two columns, its end column and whether its starts are zero-based; an index of the `vcf` or `sam` preset reads as one-based starts with no end column. |
| `check_indexed_columns` | Holds the layout flags to the table's tabix index: refuses other columns and, unless the flags name the index's own layout or single one-based positions, any end column given without `--ref-col` and any zero-based starts but those given with an end column and `--ref-col` under an index of zero-based starts, and returns the warning for single positions under an index that declares more. |
| `stream_table`          | Reads the BGZF input once and gives each row to the store's stream as it is read, with the SHA256 and length of the bytes read. |
| `Spans`                 | Records each row's start and end in a scratch file of its chromosome, for the verification's probes. |
| `read_tabix_records`    | The read that keeps every record, grouped by chromosome and sorted by start; built for the tests alone, as the reference the streamed store is compared with. |
| `open_table`            | Opens the input with `TabixAnnotator`, lines handed over as to a plugin, before the conversion reads or writes anything. |
| `verify_concordance`    | Reopens the store with `BinaryAnnotator` and compares its records with the table's at the probed positions.   |
| `probe_positions`       | The positions probed: every record start, or every n-th past 1,000 without `--verify-all`, and each of its records' end, midpoint and the positions on either side of its span, the one past its end only where the table's index holds it. |
| `verify_probes`         | Compares the store's answers with the table's at each position: a single query, a batch of the position alone, and batches of 64 positions in order and reversed. |
| `record_line`           | A record as one comparable line: its span and its cells, the chromosome cell restored from the record's chromosome. |
| `remove_store`          | Removes the store's two files, at the paths the writer published them at, after a verification that mismatches or does not run to its end. |
| `convert_cache`         | Creates the output directory, marks it as a conversion that has not ended (`CacheManifest::mark_unfinished`), removes an earlier run's `info.json`, runs `convert_data_files` over `transcripts/`, `copy_variation_files` over `variations/` and `copy_regulatory_files` over `regulatory/`, then `copy_info_json`, and last writes `CHECKSUMS.sha256` over every file of the output directory (`vep_core::cache_manifest::CacheManifest::write`); a conversion that copied a translation without its `seq_edits` list ends on one warning that counts them. |
| `read_info_json`        | Reads and parses `info.json`, checks it with `validate_info` and logs `species` and `assembly`; its `SourceInfo` carries the text and the parsed value. |
| `copy_info_json`        | Writes `info.json` with its `regulatory` marker set when regulatory shards were written (`cell_types` and `regulatory_schema` pass through) and the three keys removed otherwise, names `seq_edits` under `left_out` when a copied translation holds no list of them, and copies `chr_synonyms.txt`. |
| `copy_regulatory_files` | Refuses a regulatory tree without the schema this build reads, copies `regulatory/binding_matrices.json`, then each `regulatory/<chr>/<start>-<end>.json` or `.json.gz` shard byte for byte once it parses as the annotator parses a shard; returns the count written. |
| `regulatory_shard_range` | The `(start, end)` range a regulatory shard's name carries, `<start>-<end>.json` or `.json.gz`; none for any other name. |
| `warn_of_stray_regulatory_file` | Warns of a file directly under `regulatory/` other than the binding matrices table. |
| `validate_info`         | Checks that `info.json` is an object with a non-empty `species` and `assembly`, that `contig_order`, `variation_cols`, `cell_types` and `left_out`, when present, are lists of strings, that `regulatory_schema`, when present, is a whole number, and that `bam` and `source_type`, when present, are strings. |
| `convert_data_files`    | Re-shelves each `{chr}_{start}-{end}.json` region file as `<chr>/<start>-<end>.json`, counting entries and those among them that `lacks_seq_edits` holds. |
| `lacks_seq_edits`       | Whether a transcript record holds a translated peptide and no `seq_edits` list.                              |
| `parse_region_filename` | Splits a region file stem at its last underscore into `(chromosome, start, end)`.                           |
| `copy_variation_files`  | Copies `all_vars.gz` with its index, or the `_var.gz` region files, into `variations/<chr>/`; refuses a `.json` and an unindexed `all_vars.gz`. |
| `variation_file_kind`   | The `VariationFileKind` a name denotes: `all_vars.gz`, its `.csi` or `.tbi` index, or a `<start>-<end>_var.gz` region file; none for any other name. |
| `json_shard_error`      | The error refusing a `.json` file under `variations/`.                                                      |
| `split_flat_variation_name` | Splits a flat `{chr}_<variation file>` name into the chromosome and the file's name under `variations/<chr>/`. |

## Command line

`vep-cache-converter --help` and `vep-cache-converter convert-plugin-data --help` print the two flag sets. Diagnostics go to stderr through `tracing` at INFO level; the direct writes are the mismatch listing of a failed verification and the line a failed run ends with. A failed run of either mode exits 1 after one line, `ERROR: [cache-converter] <message>`, where `<message>` is the failure and its causes, outermost first, joined by `: `. A line stderr refuses, on a device that refuses every write or a pipe whose reader has gone, is dropped: the conversion goes on and keeps its exit status (`vep_core::stderr`).

Cache mode (no subcommand):

| Flag                   | Role                                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------------------- |
| `--json-dir <JSON_DIR>` | The flat cache: `{chr}_{start}-{end}.json` region files under `transcripts/`, the dumper's variation files under `variations/`. |
| `--output-dir <OUTPUT_DIR>` | Where the per-chromosome layout, the copied `info.json` and `chr_synonyms.txt`, then `CHECKSUMS.sha256` are written. Required. |

`convert-plugin-data`:

| Flag                  | Role                                                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------ |
| `--input <INPUT>`     | The tabix-indexed TSV (tab-separated values) or VCF (Variant Call Format) file, `.tsv.gz` or `.vcf.gz`.      |
| `--output <OUTPUT>`   | The `.vpd` data file; the `.vpdi` index is written beside it. Neither path may be the input table or a path its index is read from. |
| `--chr-col <CHR_COL>` | 0-based column index of the chromosome. Default `0`.                                                         |
| `--start-col <START_COL>` | 0-based column index of the start position. Default `1`.                                                     |
| `--end-col <END_COL>` | 0-based column index of the end position; omitted, the end equals the start. With `--ref-col` the column is a VCF INFO column, read for its `END` key, the reference allele's span otherwise; without it the cell is read to its leading integer. |
| `--ref-col <REF_COL>` | 0-based column index of the reference allele (a VCF REF column), read beside `--end-col`: its length spans a record whose end column holds no `END` at or past the start. |
| `--zero-based`        | Positions are 0-based, as in BED (Browser Extensible Data); one is added. Default: 1-based.                  |
| `--verify-all`        | Verify every record after writing, not a sample of at most 1,000 record starts.                              |
| `--no-verify`         | Skip verification.                                                                                           |

The `vep` flags that consume the outputs, `--json_cache` for the cache and `--plugin` for a store, are in [docs/cli-reference.md](../../docs/cli-reference.md).

## Run it

```bash
cargo build -p vep-cache-converter
cargo test -p vep-cache-converter
target/debug/vep-cache-converter --help
```

```bash
# Re-shelve a flat JSON cache into the layout `--json_cache` reads
vep-cache-converter --json-dir /path/to/flat_cache --output-dir /path/to/json_cache

# Build a binary store beside a plugin data file. A plugin reads the store when it
# is named after the data file with `.vpd` in place of `.gz` or `.bgz`.
vep-cache-converter convert-plugin-data \
  --input whole_genome_SNVs.tsv.gz \
  --output whole_genome_SNVs.tsv.vpd
```

The unit tests cover `convert_plugin_data`, `check_indexed_columns`, `stream_table`, `Spans`, `read_tabix_records`, `open_table`, `verify_concordance`, `probe_positions`, `verify_probes`, `remove_store`, `convert_cache`, `read_info_json`, `copy_info_json`, `copy_regulatory_files`, `regulatory_shard_range`, `validate_info`, `convert_data_files`, `parse_region_filename`, `copy_variation_files`, `variation_file_kind`, `split_flat_variation_name`, `log_lines_carry_colour`, `counted` and `counted_as`; `tests/log_lines.rs` holds the whole log of a conversion, sent to a file and to a pipe, to plain text, and the whole log of a cache of one chromosome to counts of one in the singular, as `tests/plugin_intervals.rs` holds the log of a table of one record. The workspace's standard build, test, lint and format commands are in [the contributing guide](../../CONTRIBUTING.md).
