# vep-core

The data model of vep-rs, a Rust reimplementation of the Ensembl Variant Effect Predictor (VEP): the variant, transcript, consequence and coordinate types every other crate reads and writes, plus the shared structural-variant, codon and prediction-matrix rules. All eight sibling crates depend on it: `vep-io` and `vep-cli` build an `InputVariant` from each input line, `vep-effects` fills it with `TranscriptConsequence` rows, and `vep-cli`, `vep-builtins` and `vep-plugin` read and extend those rows. The crate's product is the in-memory record the writers print.

Throughout this README "Ensembl VEP" is the reference implementation, `ensemblorg/ensembl-vep` release 116.3, the engine the [root README](../../README.md) measures vep-rs against.

## How it works

Take the VCF (Variant Call Format) line `chr21 25000100 . ACG A . . .`, a two-base deletion. The VCF reader in `vep-cli` hands the `POS` text to `coordinate::parse_pos`, which accepts any spelling that names an exact integer, the way Perl numifies the column (`3e7` is a position, `30425949.5` is not), and the `INFO` text to a `vcf_info::InfoFields` view, split once by its first lookup, whose `value("SVTYPE")` is the last `SVTYPE` as Ensembl VEP's hash would hold it. `sv_routing::written_alts` splits the `ALT` column as Perl's `split` does, and `sv_routing::routes_to_structural` answers whether the line is a structural record; here `REF` and `ALT` are plain `ACGT` runs, so the reader trims the shared `A`, computes the one-based inclusive span and calls `InputVariant::new`, which normalises `chr21` to `21` through `coordinate::normalize_chromosome`, keeps `chr21` in `original_chr` for output, builds the allele string `CG/-` through `allele_pair` and classifies the pair as `VariantClass::Deletion` through `classify_variant`. The variant then reaches `vep-effects`, which reads each overlapping `Transcript` (exons, introns, the coordinate mapper and translateable sequence of its `TranscriptVEFC`, loaded by `vep-cli` from the cache), takes the per-transcript facts from `Transcript::facts()` once per transcript, translates reference and alternate codons through `codon::translate_codon_with_table` under the transcript's codon table, and pushes one `TranscriptConsequence` per transcript into `transcript_consequences`, each carrying a `ConsequenceList` of Sequence Ontology (SO) terms whose `rank()` and `impact()` follow Ensembl Variation's table. Plugins add `plugin_data` entries to the variant or to a consequence row. The writers finish the record through `location()`, `uploaded_variation()`, `display_allele()` and `Consequence::so_term()`. Had the `ALT` been the symbolic `<DEL>`, `routes_to_structural` would have sent the line to `sv_record::structural_variants`, which gives the record one SO term and class through `sv_routing::sv_type_abbreviation` and `sv_so_term_and_class`, spans each allele from `POS` + 1 through `sv_span::structural_start` and `structural_end` and builds a breakpoint record's own breakend and its mates; a `<CNV:TR>` record read with a reference sequence to hand is expanded first by `sv_record::tandem_repeat_allele_string` into the explicit alleles of a sequence record.

## Modules

| Module           | Role                                                                                                                                                                                                                  |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lib.rs`         | Module list and the Ensembl VEP release the binary reports, as the constants `VEP_VERSION` and `VEP_SUB_VERSION`, with that release's API module versions as `VEP_API_MODULE_VERSIONS`                                |
| `allele.rs`      | Shared-prefix and suffix trimming to VEP-style minimised alleles (`"-"` for an empty side), transition versus transversion classification, IUPAC (International Union of Pure and Applied Chemistry) ambiguity codes |
| `assembly.rs`    | `Assembly`, the reference genome parsed from a run's assembly name (the cache's own, else the value of `--assembly`) by its whole aliases (`GRCh37`, `hg19` and `37` are one value) with its Ensembl and UCSC (University of California, Santa Cruz) names |
| `binding_matrix.rs` | `BindingMatrix`, a transcription factor binding matrix as the regulatory cache stores it, kept once per matrix in the cache's binding-matrices file and named by each motif feature through its stable id: the nucleotide counts by position, the descriptive fields and the complexes that bind it, the scoring tables derived from the counts, and the two scores Ensembl VEP reads from them, `relative_similarity` (a sequence's similarity to the matrix relative to its best and worst sites) and `is_position_informative` |
| `cache_info.rs`  | `CacheInfo`, the metadata a cache directory's `info.txt` or `info.json` carries: species, assembly, version, prediction availability, variation columns, the `regulatory` marker, source versions, contig order, the names of what the cache's maker left out |
| `cache_manifest.rs` | `CacheManifest`, the cache's checksum manifest (`CHECKSUMS.sha256`, beside `info.json`): one `sha256sum` line per file the cache holds, written last by the cache tools and verified by an annotation run for each file it reads whole; a file whose digest differs from its entry and a file the manifest does not list are the same refusal, a cache without the manifest passes every check, and a directory whose manifest is the one line a build writes before its first file is refused by name as a build left early |
| `codon.rs`       | Codon translation under every genetic code of BioPerl's `Bio::Tools::CodonTable` (the 18 tables of ids 1 to 24 that it ships, the standard code the default) and under NCBI's genetic code 26, each table's start and stop codons, complement and reverse complement, three-letter amino acid names |
| `consequence.rs` | The 41 SO consequence terms with rank, impact, accession and text; `TranscriptConsequence`, the row the effects engine produces, with `FeatureType` (whose order is the order a record's rows print in) and `MotifFields`, a motif row's matrix fields; `LofteeContext`, the transcript structure the built-in plugins that read the transcript model (LoFTEE among them) find on a row |

| `minimal.rs`     | `--minimal` over one record's alleles: `trim_sequences`, the minimisation of a bi-allelic record and the per-allele split of a multi-allelic one, as Ensembl VEP minimises in its parser and its input buffer                        |

| `prediction.rs`  | Decoder for the gzip-compressed SIFT (Sorting Intolerant From Tolerant) and PolyPhen prediction matrices embedded in the cache, and the Ensembl VEP-style formatting of a score                                        |

## Public API

The items a caller reaches for, by module. The record types implement `serde::Serialize`; `Transcript`, `CachedVariation` and `CacheInfo` also derive `serde::Deserialize`, while `InputVariant` and `TranscriptConsequence` are written and never read back. Those two are the JSON (JavaScript Object Notation) documents a dynamic-library plugin receives ([docs/developers/writing-a-plugin.md](../../docs/developers/writing-a-plugin.md#what-run-receives)); a `TranscriptConsequence` holds a shared handle on its `Transcript` and reads the transcript's values through accessors of the same names (`transcript_id()`, `gene_symbol()`, `biotype()`, `flags()`, `mane_select()`, ...).

| Item                                                             | Module        | What it gives a caller                                                                                                                                   |
| ---------------------------------------------------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `InputVariant`                                                   | `variant`     | One allele of one input record: coordinates, alleles, class, `transcript_consequences` (transcript, regulatory and motif rows alike), `intergenic_overlap` (the allele overlaps no transcript and keeps its intergenic row beside its regulatory rows), `colocated_variants`, `plugin_data`, the structural-variant fields |
| `InputVariant::new`, `InputVariant::without_allele`, `allele_pair` | `variant`   | Build a variant from a chromosome, span and allele pair; build the no-allele record of a non-variant line (`ALT` `.`) over its reference; the `reference/alt` string `new` gives `allele_string`, built from the two alleles' bytes |
| `location`, `uploaded_variation`, `variation_name`, `display_allele` | `variant` | The Location, `Uploaded_variation`, JSON `id` and Allele columns as Ensembl VEP prints them                                                                |
| `first_vcf_id`, `id_names_record`                                | `variant`     | A VCF record's name as Ensembl VEP's parser stores it (the first `;`-joined ID, `.` and `0` kept, an empty field or element none) and whether a stored name names its record in `Uploaded_variation` and as a mate stand-in (Perl-true and not `.`) |

| `Consequence`, `ConsequenceList`, `Impact`                       | `consequence` | The 41 terms with `rank()`, `impact()`, `so_term()`, `so_accession()`, `from_so_term()` and `most_severe()`; `Ord` follows rank                          |
| `TranscriptConsequence`, `FeatureType`, `MotifFields`            | `consequence` | One row of annotation against a transcript, regulatory feature or motif feature: the transcript's values through accessors on a shared handle (`for_transcript`), a regulatory or motif row's `feature_id` and a regulatory row's `feature_biotype`, `feature_overlap()` for the structural-variant overlap columns, `ensembl_vep_key()` for the key Ensembl VEP sorts a record's rows of one kind by (a transcript's stable id with `_` and its database id, a regulatory feature's stable id, a motif's database id, held in `motif_db_id`), `structural_feature_order()` for the order of a structural variant's regulatory and motif rows (the met rank in `id_rank`, then the start and the stable id); `FeatureType`'s `Ord` is the order a record's rows print in (transcript, regulatory, motif); `MotifFields` carries a sequence variant's motif row's `MOTIF_NAME`, `MOTIF_POS`, `HIGH_INF_POS`, `MOTIF_SCORE_CHANGE` and `TRANSCRIPTION_FACTORS` |

| `structural_variants`, `tandem_repeat_allele_string`, `tandem_repeat_stated_bases`, `tandem_repeat_alleles_as_long_as_the_run`, `parse_ci_field` | `sv_record` | The variants of one structural record, a `<CNV:TR>` record's allele string over its reference run, the bases each of its alleles states for itself and which of its alleles are exactly as long as that run, each read from the record's `InfoFields`; a `CIPOS` or `CIEND` pair |

| `InfoFields`, `info_field`, `info_value`, `info_value_written`   | `vcf_info`    | One record's `INFO` column, split once and read by every lookup, and single-key scans of it: a key as Ensembl VEP's hash holds it, flag, written value or absent |

## Run it

The crate follows the workspace's standard commands ([the contributing guide](../../CONTRIBUTING.md)). Scoped to this crate:

```bash
cargo build -p vep-core
cargo test -p vep-core
cargo doc --no-deps -p vep-core
```

`cargo test -p vep-core` runs the modules' unit tests and `tests/prediction_fixtures.rs`, which decodes two prediction matrices taken from Ensembl's public variation database and checks their per-category counts and sampled cells against the packing rule of Ensembl's `ProteinFunctionPredictionMatrix.pm`.
