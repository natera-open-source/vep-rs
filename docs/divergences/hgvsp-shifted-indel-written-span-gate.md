# The HGVSp of an insertion or deletion shifted from an intron into the coding sequence

**The defect in one sentence.** Under `--hgvs`, Ensembl VEP 116.2 writes the HGVSc of the shifted change and no HGVSp for an insertion or deletion that the record writes in an intron inside the coding region and the 3' shift carries wholly into the coding sequence. It fills the HGVSp only on a transcript that has an intron of 13 bases or fewer, for an allele written within 12 bases of an exon. For such an insertion or deletion vep-rs writes the protein notation of the shifted change.

**Why this is a defect.** HGVS describes an insertion or deletion at its most 3' position, and both engines shift the allele there before writing a notation. On these rows that position lies in the coding sequence. The row's HGVSc describes the change there, and its `HGVS_OFFSET` gives the number of bases the shift moved it. Ensembl VEP reads the translation start and end, the first and last residue of the change, at the shifted position. The one test that empties the field asks whether the allele is coding, and Ensembl VEP makes it on the allele as the record writes it, in the intron. For the same change given at the shifted position it writes the protein notation.

The protein notation is the predicted consequence of the change that the HGVSc describes. An empty HGVSp contradicts no HGVS recommendation: the row omits a description that the nomenclature gives. The defect is the inconsistency inside Ensembl VEP's own row, between the shift it applies and the coding test it makes on the allele as written.

On a transcript that has an intron of 13 bases or fewer, which Ensembl VEP's source calls a frameshift intron, the test widens the allele's span by 12 bases before it looks for an exon. An allele written in an intron inside the coding region, within 12 bases of an exon, then passes. Ensembl VEP writes its HGVSp when the translation start and end exist at the shifted position: the method computes the notation wherever its test lets the row through.

**What vep-rs does instead.** vep-rs writes the protein notation of the shifted change. It is the predicted consequence that the nomenclature gives for the description in the row's HGVSc, the one Ensembl VEP omits, and the value both engines write for the change given at the shifted position. vep-rs writes it where three things hold. The record writes the allele in an intron inside the coding region. The shifted change lies wholly in the coding sequence, as a deletion of coding bases or an insertion between two coding bases. The transcript's coding sequence is complete. Where the first two hold and Ensembl VEP's wider test fills the HGVSp, vep-rs writes the same notation.

A coding sequence is complete when its last three bases are a stop codon and the transcript carries neither the flag `cds_start_NF` nor the flag `cds_end_NF`, which mark a coding sequence incomplete at its start or its end. On a transcript that carries one of the flags, and on one whose coding sequence does not end in a stop codon, vep-rs leaves the HGVSp empty on every row on which Ensembl VEP leaves it empty, with one exception. With that exception set apart, the engines agree on the HGVSp of every such row.

The exception is a change of the stop codon. On a transcript that carries one of the flags and whose coding sequence is a whole number of codons, the last of them a stop codon, a shifted change can leave every residue before the stop codon as it is. vep-rs gives such a change the notation it has on a complete transcript, beside Ensembl VEP's empty field.

The exception reaches no other incomplete coding sequence: one that is not a whole number of codons, or that does not end in a stop codon, keeps the empty HGVSp. The comparison sets aside no row of the exception, since the class described below takes no row whose `FLAGS` field names one of the flags. On any transcript, the class also takes no row whose notation starts at the stop codon, names it as a flank of an insertion, or names it as the end of a duplicated, deleted or replaced range.

Two more kinds of row keep an empty HGVSp in vep-rs. The first is an insertion that the record writes inside an intron and that the shift leaves between the intron's last base and the exon's first base. Ensembl VEP writes no HGVSp for such an insertion either on a transcript that has no intron of 13 bases or fewer. Where Ensembl VEP does write one, the row is a difference that the class does not take. The second is an allele written in an intron of the 5' UTR, which the shift carries over the exon's UTR bases into the coding sequence: both engines leave its HGVSp empty.

Where vep-rs writes the notation, nothing else in the row changes: the consequence terms and the empty position columns stay those of the allele as written, as in Ensembl VEP's row.

**Where it is in Ensembl VEP's source** (`ensembl-variation` at release/116):

- `Bio/EnsEMBL/Variation/TranscriptVariationAllele.pm`, lines 1657-1822, `hgvs_protein`: line 1711 shifts the allele 3'. Lines 1730-1738 return nothing unless the `coding` predicate holds (line 1731) and a translation start and end exist (lines 1732-1733). The start and end are read at the shifted position; the predicate is not.
- `Bio/EnsEMBL/Variation/BaseVariationFeatureOverlapAllele.pm`, lines 337-398, `_pre_consequence_predicates`: line 340 computes the predicates only when the allele has none, and line 394 keeps them. They are computed for the row's consequence terms, which are filled before the HGVS fields, so they exist before line 1711 shifts the allele.
- The same file, lines 454-571, `_bvfo_preds`: line 460 takes a shift only from an allele that was shifted when the predicates are computed, which `TranscriptVariation.pm`, lines 132-135, does only under `--shift_3prime 1`. The span of line 462 is therefore the written one. Lines 511-516 set `exon` from the exons that span overlaps, and lines 535-537 set `non_coding` when it overlaps none; `coding` is then never set.
- `Bio/EnsEMBL/Variation/BaseTranscriptVariation.pm`, lines 988-1040, `_create_intron_trees`: lines 1032-1035 set `_has_frameshift_intron` on a transcript where an intron's end lies at most 12 above its start, an intron of 13 bases or fewer.
- The same file, lines 848-870, `_overlapped_exons`: on such a transcript line 861 sets a stretch of 12, and lines 863-866 fetch the exons that overlap the span widened by it. An allele written in an intron within 12 bases of an exon then gets `exon` at lines 511-516 and `coding` at lines 540-557, and line 1731 passes.

**What correcting it would change.** With the coding test made on the shifted change, these rows would carry the notation Ensembl VEP writes when the record gives the change at the shifted position. The engines' rows differ in the HGVSp alone, so no other column would change.

**The class it produces.** `hgvsp_shifted_indel_written_span_gate` sets aside a protein notation in vep-rs's `HGVSp` against an empty `HGVSp` in Ensembl VEP's. The row is that of an insertion or deletion, annotated inside the transcript, with no cDNA, CDS or protein position. Both engines' rows hold the same HGVSc and the same non-zero `HGVS_OFFSET`. The HGVSc places the shifted change in the coding sequence: a deletion of coding bases alone, a duplication that ends on a coding base, or an insertion between two coding bases.

The class reads the two rows and no transcript model, so the notation has to show that the intron lies inside the coding region: the exon the change is shifted into must open at coding base 2 or later. A duplication whose first coordinate lies in the intron names that exon's first base. Any other notation gives a lower bound for it: the first coding base of a deletion, or the coding base after a duplication or an insertion, less the offset, plus 1. A row whose offset is too long for that bound to reach 2 is not set aside.

Three kinds of row are not in the class, and a protein notation on one side alone is a difference on each. The first is an insertion that the shift leaves between an intron's last base and the exon's first base, whatever bases it inserts and however long the shift. Its HGVSc is a duplication that ends on the intron's last base, or an insertion between that base and the exon's first. The second is a row on which vep-rs's notation starts at the stop codon, names it as a flank of an insertion, or names it as the end of a duplicated, deleted or replaced range.

The third is a row whose `FLAGS` field names `cds_start_NF` or `cds_end_NF` in either engine's output. The exception for a change of the stop codon applies only on a transcript that carries one of those flags, so the class takes none of its rows. On a transcript that carries neither flag, a coding sequence that does not end in a stop codon shows in no field of a row, so the class has no test for it. vep-rs writes no notation of its own there, and the engines' rows agree.

A notation on Ensembl VEP's side against none on vep-rs's and two notations that differ are differences as well. A row whose `SHIFT_LENGTH` field is positive was annotated at the shifted position, as under `--shift_3prime 1`, and is not in the class either.

The class is built into the format comparator, `scripts/concordance/compare_vep_formats.py`, which holds Ensembl VEP's output against vep-rs's and applies the class row by row. The concordance figures that compare vep-rs with Ensembl VEP are scored on sets of consequence terms, so the HGVSp never enters them.

Four worked examples follow. In them, angle brackets hold a notation described in words.

## 1. The last base of an intron of ENST00000265857, deleted

**In short.** On GRCh37, the record at chromosome 7, position 934969, has a two-base reference allele and a one-base alternate. It deletes the base at 934970, the last base of intron 8 of the forward-strand transcript ENST00000265857. That base and the two after it are one and the same base, so the 3' rule carries the deletion two bases on: it becomes the deletion of coding base 897, the second base of exon 9. Under `--hgvs` each engine's row holds `splice_acceptor_variant`, no cDNA, CDS or protein position, `HGVSc=<the deletion of coding base 897>` and `HGVS_OFFSET=2`. The HGVSp is empty in Ensembl VEP's row and `<a frameshift at residue 300 with a new stop 3 residues on>` in vep-rs's.

A record at 934971 with a two-base reference allele and a one-base alternate gives the same deletion at the shifted position. Both engines annotate it `frameshift_variant,splice_region_variant` at `Protein_position` 299, with the HGVSp that vep-rs writes for the record in the intron. Coding base 897 is the third base of codon 299, and the notation names residue 300, the first residue the frameshift changes. In the written record the deleted base lies in no exon, so lines 511-516 leave `exon` at 0 and lines 535-537 set `non_coding`. The test of line 1731 fails, although lines 1732-1733 find residue 299 at the shifted position.

## 2. Thirty-one bases inserted 16 bases before an exon of ENST00000164305

**In short.** On GRCh37, the record at chromosome 15, position 55642880, has a one-base reference allele and a 32-base alternate. It inserts 31 bases between 55642880 and 55642881, 17 and 16 bases before exon 10 of the forward-strand transcript ENST00000164305. The inserted bases repeat the 31 reference bases after them, so the 3' rule carries the insertion 31 bases on, to stand between coding bases 1138 and 1139. Under `--hgvs` each engine's row holds `splice_polypyrimidine_tract_variant,intron_variant`, no cDNA, CDS or protein position, `HGVSc=<a duplication from 16 bases before coding base 1124 to coding base 1138>` and `HGVS_OFFSET=31`. The HGVSp is empty in Ensembl VEP's row and `<a frameshift at residue 380 with a new stop 44 residues on>` in vep-rs's.

For the insertion given at the shifted position, both engines write `frameshift_variant`, `Protein_position` 380 and the HGVSp that vep-rs writes for the record in the intron. The duplicated bases are the last 16 of the intron and the first 15 of exon 10. The notation's first coordinate therefore lies in the intron and names coding base 1124 as the exon's first base, which is the base the class reads: the exon opens later than coding base 2.

## 3. One deletion on two transcripts, one of them with an intron of one base

**In short.** On GRCh37, the record at chromosome 7, position 21934500, deletes the base at 21934501, the last base of an intron in two forward-strand transcripts of one gene. The 3' rule carries the deletion four bases on, into the exon that follows: it deletes coding base 12958 of ENST00000328843 and coding base 12937 of ENST00000409508. On ENST00000328843, which has an intron one base long, both engines write `HGVSp=<a frameshift at residue 4320 with a new stop 15 residues on>`. On ENST00000409508 the HGVSp is empty in Ensembl VEP's row and `<a frameshift at residue 4313 with a new stop 15 residues on>` in vep-rs's.

The record holds a two-base reference allele and a one-base alternate. On both rows each engine writes `splice_acceptor_variant`, the HGVSc of the deletion of that coding base and `HGVS_OFFSET=4`. The one-base intron of ENST00000328843 makes lines 1032-1035 set `_has_frameshift_intron` on it, and lines 861-866 widen the span by 12 bases: the deleted base, one base before the exon, gets `exon` and `coding`, and the test of line 1731 passes. In a run of Ensembl VEP with that stretch set to 0, the HGVSp on ENST00000328843 is empty as well. ENST00000409508 has no intron of 13 bases or fewer, and the test fails there as in example 1.

For the deletion given at the shifted position, both engines write `frameshift_variant` and those two notations, one on each transcript. Ensembl VEP's wider test is the subject of [another page](hgvsp-coding-test-widened-by-a-short-intron.md); this example shows only that the row on ENST00000409508 is of this class.

## 4. Two bases deleted on ENST00000397591, whose coding sequence is not complete

**In short.** On GRCh37, the record at chromosome 15, position 39874391, has a three-base reference allele and a one-base alternate. It deletes the bases at 39874392 and 39874393, the last two bases of intron 2 of the forward-strand transcript ENST00000397591. The transcript carries the flag `cds_end_NF`, and its coding sequence does not end in a stop codon. The 3' rule moves the deletion two bases on, to coding bases 68 and 69 in exon 3. Both engines write the HGVSc of the deletion of those two coding bases, and both leave the HGVSp empty.

The transcript has no intron of 13 bases or fewer, so Ensembl VEP's test fails as in example 1. vep-rs leaves the field empty because the coding sequence is not complete. Given at the shifted position, the deletion gets `HGVSp=<a frameshift at residue 23 with a new stop 9 residues on>` from both engines. The engines agree on the written row, so nothing is there for the class to set aside, and the class takes no row whose `FLAGS` field names the flag.
