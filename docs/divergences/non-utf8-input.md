# Input bytes that are not UTF-8

Ensembl VEP writes an input byte that is not UTF-8 as the byte it read, in every format. vep-rs carries such a byte unchanged in a VCF written from a VCF and prints the replacement character U+FFFD in its place in the other outputs. A difference in the text of a field, not in any tuple: the comparators key rows by Location, Allele and Feature, which are ASCII, and nothing is set aside. The one key such a byte can reach is the Feature of a `--regulatory_gff` record whose identifier holds it, below.

Ensembl VEP opens its input with no decoding layer (`Parser.pm` lines 235-242 for standard input and a compressed file, `ensembl-io`'s `TextParser.pm` line 70 for a plain file) and writes the bytes it read. A Latin-1 `é` (the byte `0xE9`) in a header line, an ID, an INFO value or a sample name comes out as that byte in every format. In the JSON output that byte leaves the document invalid as UTF-8.

vep-rs reads the input as bytes and writes the VCF output as bytes. The header block carries the input's `##` lines and sample names unchanged. Every record line, annotated or a non-variant record kept by `--allow_non_variant`, is the line as Ensembl VEP stores it, each column the bytes it was read from, with the annotation appended to INFO. A trailing empty column is dropped, and a structural record's QUAL, FILTER and INFO read `.` where absent, empty or `0`. So a VCF written from a VCF carries every input byte of the columns it stores.

A record is otherwise read as UTF-8 with each invalid sequence replaced by U+FFFD, sample columns included. An ID, an INFO value or a genotype field that is not UTF-8 prints the replacement character in `Uploaded_variation`, in the JSON `input` string (`serde_json` writes UTF-8 alone) and in a warning that quotes the line. Of those columns the default and tab outputs print the ID alone. A record of another input format is read as text throughout, so its name reaches the ID column of the VCF line built for it with the replacement character too.

The flat files the built-in plugins and `--custom` sources read follow the same rule. An Ensembl VEP plugin opens its file with no decoding layer, and a tabix-indexed file's header comes through `tabix` (`pLI.pm` lines 124 and 140, `LoFtool.pm` line 82, `DosageSensitivity.pm` line 131, `GWAS.pm` lines 367 and 370, `UTRAnnotator.pm` line 93, `MaxEntScan.pm` line 737). vep-rs reads every line of such a file as bytes too. A byte that is not UTF-8 in a comment line, in a cell no plugin reads or in a key cell changes nothing in either engine: the key names a gene no row carries. A `pLI` or `LoFtool` score is the number before the byte in both.

In a cell the plugin prints as text, a `DosageSensitivity` probability, a `GWAS` study accession, a `--custom` source's `##INFO` description or a column name of a tabix header, Ensembl VEP prints the byte and vep-rs prints U+FFFD, in every output format. A plugin data store written by `convert-plugin-data` holds such a cell as U+FFFD too, so a store and a tabix query give the same cell.

A `--regulatory_gff` or `--custom` GFF record's attribute values and type column follow the rule too. A byte that is not UTF-8 in an `ID`, `Name`, `binding_matrix_id`, `transcription_factor` or `gene_id` value prints as U+FFFD where Ensembl VEP writes the byte, so two identifiers or two types differing only in such bytes are one to vep-rs and two to Ensembl VEP. An `extended_start` or `extended_end` so read is not a whole number and is ignored with its warning ([Defect N, class 27](defect-n.md#27-a-promoter-whose-extended_start-is-not-a-number-is-widened-to-position-0)).

Both readers decode a type column's escapes, and an attribute value's, over the record's bytes, so an escape completing a raw first byte of a character forms the character as Ensembl VEP's bytes do. `vep-cache-builder` decodes the escapes the same way and refuses a line holding such a byte raw, naming the line. Its regulatory bake skips such a line of a type it does not keep, as the run-time reader does. A type that is not UTF-8 once decoded matches no accepted type in either engine, so both skip the record with their warning, vep-rs naming the type with U+FFFD.

A `MaxEntScan` matrix line holding such a byte is refused by vep-rs when the plugin opens. A score line is refused as not a number, where Ensembl VEP reads the number before the byte. A 7-mer line is refused as not a 7-mer, where Ensembl VEP keys the line as written (`MaxEntScan.pm` line 741) and later fails every variant whose 7-mer that line held (`No score5_seq`, line 684), a `went wrong` warning and no score on the row.

A file that is UTF-8 throughout, non-ASCII characters included, is written by both engines as read.
