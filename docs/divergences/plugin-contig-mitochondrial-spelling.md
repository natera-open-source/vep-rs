# A mitochondrial record against a plugin's file naming the contig under another spelling

**The defect in one sentence.** Ensembl VEP keeps a mitochondrial record under its own spelling, `MT`, `chrM` or `chrMT`, and its tabix-backed plugins map it one step only, so a file naming the sequence otherwise silently yields nothing, where vep-rs writes the plugin's field on GRCh38, and AlphaMissense's on GRCh37.

**Why this is a defect.** On GRCh38 the four names denote one sequence, a fact the engine itself holds. Its parser keeps a record written `chrM` through the cache's synonym table and one written `chrMT` through its `chr` rule, and has a rule renaming a bare `M` to `MT`. Its own name resolver, the one the cache, a `--custom` file and the FASTA are read through, tries the synonyms before the `chr` step. The plugin base class is a copy of that resolver without the synonym step: it tries the record's spelling and its `chr` variant and nothing else. A record on `MT` so reaches a file naming `MT` or `chrMT` and never one naming `chrM` or `M`.

In one run the record is annotated from the cache, read from a `chrM`-named custom file and skipped by a `chrM`-named plugin file, with no field and no warning; the empty result is indistinguishable from a site the file lacks.

**Where the names are two sequences.** On GRCh37 the four names are not one sequence. `MT` and `chrMT` name the assembly's mitochondrial sequence, NC_012920.1, of 16,569 bases. `chrM` and `M` are the UCSC hg19 spelling of NC_001807.4, of 16,571 bases. The two differ by four insertions or deletions and by 38 bases, and at each of the 11,341 coding positions a base of NC_001807.4 stands one position after the assembly's. A table whose rows count on that sequence holds, at a record's position on `MT`, the row of the neighbouring base. There the base class's one step keeps the two sequences apart and is no defect: reading across the names would write another position's value.

One published table is shown to count otherwise. The AlphaMissense table of GRCh37 spells the contig `chrM`, and the reference allele of each of its 24,074 mitochondrial rows is the assembly's base at the row's own position; the rows stand at the positions and alleles of the GRCh38 table's. For that table the names are one sequence on GRCh37 as well, and Ensembl VEP's miss is the defect it is on GRCh38.

**What vep-rs does instead.** vep-rs names the record's chromosome as the cache names it before any lookup, `MT` here. On GRCh38 it queries a plugin's file under `MT`, `chrMT`, `M` and `chrM`, so every spelling of the record reaches every spelling of the file; the output keeps the input's spelling. On GRCh37 it reads a table's mitochondrial rows under the record's own spelling and its `chr` variant alone, as Ensembl VEP does, and across the two pairs of names for AlphaMissense, whose table is shown above to count on the assembly's sequence. dbNSFP and gnomADMt, whose modules name a mitochondrial record `M` themselves, are read under every spelling on both assemblies.

**Where it is in Ensembl VEP's source** (`ensembl-vep` at release/116.2, `ensembl-variation` at release/116, `VEP_plugins` at release/116):

- `Bio/EnsEMBL/VEP/Parser.pm`, lines 770-802, `_have_chr`: a record spelt `MT`, `chrM` (a synonym the cache's `chr_synonyms.txt` lists) or `chrMT` (the `chr` rule) is kept under its own spelling; only a bare `M` is renamed, and only when the synonyms miss (lines 794-797).
- `Bio/EnsEMBL/VEP/Parser/VCF.pm`, lines 249 and 348: the record's chromosome is the CHROM column as written.
- `Bio/EnsEMBL/Variation/Utils/BaseVepTabixPlugin.pm`, lines 693-708, `_get_source_chr_name`: a name the file lacks is tried without its `chr` prefix, or with `chr` added, and nothing else; lines 594 and 599, `_get_data_hts`, query the mapped name against the file's own sequence names. `MT` reaches `MT` and `chrMT`; `chrM` reaches `chrM` and `M`.
- `Bio/EnsEMBL/VEP/BaseVEP.pm`, lines 689-738, `get_source_chr_name`: the engine's own resolver, the same code with a synonyms step first (lines 708-716), through which the cache, a `--custom` file and the FASTA reach `chrM` from `MT`. The one-row table of section 1 given as a `--custom` BED named `chrM` is read on the same record; the plugin's copy of it is not.
- `ClinPred.pm`, line 120, hands the record's name to the base class unchanged, as do `CADD.pm`, line 227, `AlphaMissense.pm`, line 248, `BayesDel.pm`, line 144, `dbscSNV.pm`, line 163, `SpliceAI.pm`, lines 232-238, and `SpliceVault.pm`, line 158.
- `OpenTargets.pm`, line 350, `PrimateAI.pm`, line 178, `TranscriptAnnotator.pm`, line 218, `REVEL.pm`, line 168, `AVI.pm`, line 138, and `LOEUF.pm`, lines 180 and 187, hand it over unchanged as well.
- Three plugins rewrite the name first. `dbNSFP.pm`, line 313, turns `MT` into `M`, so every record spelling reaches an `M`- or `chrM`-named file and none an `MT`- or `chrMT`-named one. `gnomADMt.pm`, lines 256-261, strips `chr` and turns `MT` into `M`, the mechanism of [its own class](gnomadmt-mt-named-contig.md). `gnomADc.pm`, line 158, strips a lower-case `chr` alone, so a record written `MT` never reaches the `chrM` of the published GRCh38 coverage file.

**What correcting it would change.** Where the names are one sequence, a mitochondrial record would carry the plugin fields its file holds at the position under whatever spelling the file names the contig, as its cache annotation and its `--custom` annotations do.

**The class it produces.** `plugin_contig_mitochondrial_spelling`: a field of a tabix-backed plugin other than gnomADMt that the candidate alone fills on a row of a record spelt `MT`, `chrM` or `chrMT`. Such a row arises where the plugin's data file names the mitochondrial contig under a spelling the record's own does not reach by adding or removing `chr`: on GRCh38 for any such plugin, on GRCh37 for AlphaMissense alone.

The format comparator sets such a field aside where a comparison case names the class. It reads the fields the plugins name themselves, so a column a dbNSFP run selects and a TranscriptAnnotator table's fields are not read. It compares the two outputs and never opens the data file: its test is the record's spelling and a field the candidate alone fills, and the file's spelling is not checked. Beside a corpus manifest that names GRCh37 it sets aside the AlphaMissense fields alone. A field both outputs fill, or the reference alone, stays a difference.

No committed corpus pairs a mitochondrial record with such a file: the gnomADMt corpus's slice names the contig `chrM`, which that plugin's rewrite reaches, and the dbNSFP corpus's table names it `M`, which its plugin's rewrite reaches. No other corpus that runs a tabix-backed plugin carries a mitochondrial record, and no comparison case does. The concordance figures score consequence sets and never see a plugin field.

**How often the shape occurs.** Tier 2 under the rule of [Intended divergences from Ensembl VEP](../intended-divergences.md#differences-outside-the-classes): the shape is a record spelt `MT`, `chrM` or `chrMT` run with a tabix-backed plugin whose file names the contig otherwise; a bare `M` is the [`bare_m_chromosome`](bare-m-chromosome.md) difference. 334 of the 487 mitochondrial records of the committed corpora, in 10 corpora, name the contig `MT`, `chrM` or, in the Arabidopsis corpus, `Mt`; the other 153 are the yeast corpus's `Mito`. 80 flag sets run a tabix-backed plugin other than gnomADMt, and the file's contig name then decides whether the divergence occurs.

Of the open data files the supported plugins read, the AlphaMissense tables of both assemblies and the GRCh38 gnomADc coverage file name the contig `chrM`. The REVEL, LOEUF and OpenTargets tables and the GERP table LoFTEE reads carry no mitochondrial contig, nor do the committed corpora's synthetic CADD, dbscSNV, SpliceAI and AVI tables. `dbNSFP.pm`, lines 313-314, queries `MT` under `M`. The genome-wide ClinVar datasets carry 3,122 `MT` records each, of 4,398,127 on GRCh38 and 4,388,172 on GRCh37; no chromosome 21 cut carries one. On GRCh37 a table a user prepares from files of the UCSC naming carries the contig as `M` or `chrM` on that naming's sequence, and both engines leave a record on `MT` without its fields.

## 1. ClinPred: the corpus record on `MT` against a one-row table named `chrM`

**In short.** The GRCh38 gnomADMt corpus (`tests/golden/116/GRCh38-plugin-gnomadmt/`) holds the record `MT 3460 rs199476118 G A`, a missense variant on `ENST00000361390`. The table is one synthetic ClinPred row, `chrM 3460 G A 0.5`, under the header `#chr Start Ref Alt ClinPred_Score`, compressed with `bgzip` and indexed with `tabix -s 1 -b 2 -e 2`. Ensembl VEP writes the transcript's row as `rs199476118 MT:3460 A ENST00000361390 missense_variant IMPACT=MODERATE;STRAND=1` (the identifier, location, allele, feature, consequence and extra columns). vep-rs writes the same row ending `IMPACT=MODERATE;STRAND=1;ClinPred=0.5`. With the table's contig spelt `MT` or `chrMT` both engines write `ClinPred=0.5`; spelt `M` or `chrM`, Ensembl VEP writes none.

The record written `chrM` reverses the pattern, Ensembl VEP scoring it from the `M` and `chrM` tables alone, and the record written `chrMT` scores as `MT` does. vep-rs writes `ClinPred=0.5` in all twelve cells of the three record spellings against the four table spellings. In every cell the two engines' rows agree in every other column, the plugin's header line is in every output, and neither engine warns of the lookup.

**Try it yourself.** Write the row under its header, `bgzip` and `tabix -s 1 -b 2 -e 2` the file, and run both engines with `--plugin ClinPred,file=<file>` on the record; the commands of [Reproducing these examples](reproducing.md#reproducing-these-examples) give the engines and their caches, the gnomADMt corpus's `json_cache` serving vep-rs.

## 2. AlphaMissense: the published GRCh38 table, which names the contig `chrM`

**In short.** The published AlphaMissense tables of both assemblies name the mitochondrial contig `chrM`, and the GRCh38 table carries the row `chrM 3460 G A hg38 P03886 ENST00000361390.2 A52T 0.624 likely_pathogenic`. For the record `MT 3460 rs199476118 G A` under `--plugin AlphaMissense,file=<table>`, Ensembl VEP writes the transcript's row as `rs199476118 MT:3460 A ENST00000361390 missense_variant IMPACT=MODERATE;STRAND=1`. vep-rs writes the same row ending `IMPACT=MODERATE;STRAND=1;am_class=likely_pathogenic;am_pathogenicity=0.624`. The same record written `chrM` gets the two fields from both engines, at `chrM:3460`. ClinVar names the chromosome `MT`, so on a ClinVar release every mitochondrial missense record meets the shape. The GRCh37 table holds its mitochondrial rows at the same positions and alleles, the assembly's own, and the two engines differ on it in the same way.

**Try it yourself.** Run both engines with `--plugin AlphaMissense,file=<the GRCh38 table>` on the record `MT 3460 rs199476118 G A` and again on it written `chrM`, under the caches of [Reproducing these examples](reproducing.md#reproducing-these-examples), the gnomADMt corpus's `json_cache` serving vep-rs.
